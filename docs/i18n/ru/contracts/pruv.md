# Pruv

Pruv — язык для proof-native контрактов Parano1d. Компилятор переводит изменения
состояния и явную политику расходования в действующий ABI 3. Исполнение доказывается
общим отношением блока. Программа, которая помещается в этот ABI, работает
без форка сети и обновления узлов.

## Сборка и параметры

Из корня репозитория:

```sh
cargo build --release --locked -p noid_pruv
target/release/pruv --help
```

Исполняемый файл — `pruv`, в Windows — `pruv.exe`. Для проверки постусловий
нужен локальный Z3: команда `z3` в PATH или путь через `--z3`.

Пример бюджета находится в `noid_pruv/examples/budget.pruv`. Создайте
`budget.params.json`, заменив адреса и выбрав будущую высоту восстановления:

```json
{
  "spending_key": "<o1-адрес расходующего кошелька>",
  "recovery_key": "<o1-адрес восстановления>",
  "recipient": "<o1-адрес получателя>",
  "recover_at": "<будущая высота блока>",
  "budget": "10000000",
  "max_fee": "1000000",
  "max_payment": "1000000"
}
```

Параметры `u64` передаются каноническими десятичными строками, `bool` —
значениями JSON `true` и `false`, адреса — строками `o1…`. Повторяющиеся,
неизвестные, отсутствующие и неверно типизированные параметры отклоняются.
Суммы здесь выражены в целых μNOID. Бюджет учитывает выплаты и комиссии;
`max_fee` и `max_payment` ограничивают один вызов. Фактическую комиссию
рассчитывает узел.

```sh
target/release/pruv check noid_pruv/examples/budget.pruv --params budget.params.json
target/release/pruv verify noid_pruv/examples/budget.pruv --params budget.params.json
target/release/pruv build noid_pruv/examples/budget.pruv --params budget.params.json --out budget.json
parano1d-cli contract create budget.json --out budget.opening.json
```

`check` проверяет синтаксис, типы, полноту политики и ограничения ABI.
`verify` проверяет объявленные постусловия через Z3. `build` выполняет проверки
исходника и ABI, затем сохраняет определение `custom_program` для существующего
CLI/RPC. Выходной файл должен быть новым. Без `--out` результат идёт в stdout.

## Пополнение, вызов и восстановление

Через локальный узел финансирующего кошелька:

```sh
parano1d-cli contract protocol
parano1d-cli contract fund budget.opening.json 10
parano1d-cli contract instances budget.opening.json
```

CLI принимает суммы в десятичных **NOID**, а параметры Pruv и RPC — в целых
**μNOID**. Протокол должен сообщать ABI 3 и доступный runtime. Дождитесь
подтверждения пополнения. Каждый отдельный депозит создаёт экземпляр
с собственными счётчиками и балансом.

На узле расходующего кошелька загрузите публичные условия, найдите актуальные
`slot_index` и `creation_id`, затем просмотрите выплату:

```sh
parano1d-cli contract watch budget.opening.json
parano1d-cli contract instances budget.opening.json
parano1d-cli contract call budget.opening.json <slot> <creation-id> --pay 0.1 --pay-to <o1-получатель> --preview
parano1d-cli contract call budget.opening.json <slot> <creation-id> --pay 0.1 --pay-to <o1-получатель> --expected-txid <txid-из-preview> --out call-1.json
```

Проверьте получателя, полномочия, комиссию, остаток и преемника. CLI сохраняет
просмотр до авторизации, связывает его с точной высотой и транзакцией, ждёт
подтверждения и сохраняет `call-1.receipt`. Если высота или транзакция изменилась,
нужен новый просмотр. Следующий вызов использует преемника из `call-1.json`:

```sh
parano1d-cli contract instances call-1.json
parano1d-cli contract verify call-1.receipt
```

В примере до дедлайна расходующий ключ может продолжать выплаты. На высоте
дедлайна и позже ключ восстановления может закрыть текущего преемника:

```sh
parano1d-cli contract watch call-1.json
parano1d-cli contract call call-1.json <новый-slot> <новый-creation-id> --close --preview
parano1d-cli contract call call-1.json <новый-slot> <новый-creation-id> --close --expected-txid <txid-закрытия> --out closing.json
```

Сохраняйте условия, файлы преемников и чеки. Исторический чек проверяется после
pruning; текущие права расходования проверяются по State.

## Синтаксис и инструкции

Файл содержит один `contract`, один блок `policy` и один блок `call`.
`param` объявляет внешний параметр; `const` — значение времени компиляции;
`state` — постоянный счётчик `u64`. Постоянные регистры назначаются в порядке
объявления, до двух на контракт. Каждому вызову доступны два временных регистра,
которые начинаются с нуля.

```text
call {
    when !terminal {
        require payout <= remaining;
        remaining -= payout + fee;
        calls += 1;
    }
}
ensures remaining <= old(remaining);
ensures calls >= old(calls);
```

Присваивания выполняются по порядку. `when` вычисляет условие один раз при входе;
вложенный блок сохраняет условие родителя. Арифметика пропущенной ветки неактивна.
`require` создаёт проверку при вызове контракта; ложное условие отклоняет вызов.
Операции `+` и `-` проверяют границы `u64`: переполнение или отрицательный результат
отклоняют вызов. Ошибочная константная арифметика отклоняется компилятором.

| Pruv | Нативная операция |
| --- | --- |
| `x = value` | `move` |
| `a + b`, `a - b` | `add`, `subtract` |
| `min(a, b)`, `max(a, b)` | `min`, `max` |
| `<`, `>` | `less_than`, с перестановкой операндов для `>` |
| `==` | `equal` |
| `!=`, `<=`, `>=`, `!` | Сравнение и инверсия логического значения |
| `require a == b` | `assert_equal` |
| `require a <= b`, `require a >= b` | `assert_less_or_equal` |
| Неиспользованный хвост программы | Канонические `keep` |

Одна строка исходника может потребовать несколько инструкций. Предел —
16 инструкций, два постоянных и два временных регистра. Вычисляемые и вложенные
условия тоже расходуют временные регистры. Превышение отклоняется при компиляции.
Исходник и параметры ограничены 64 KiB; исходник также ограничен 8192 токенами
и глубиной вложенности 64.

Пример бюджета занимает три инструкции. `noid_pruv/examples/instructions.pruv`
занимает 13 инструкций с дополнением `keep` и использует все десять операций ABI.

## Контекст и политика

Числовые значения контекста: `height`, `fee`, `payout`, `retained`, `input_amount`,
`input_creation_id`, `input_slot`, `retained_slot`, `payout_slot`, `payout_owner0`
— `payout_owner3`. Логические флаги: `before_deadline`, `after_deadline`,
`terminal`, `has_payout`.

`height` — высота включения. `before_deadline` означает `height < deadline_height`;
равенство уже выбирает восстановление. Контекст соответствует физическим
выходам: при закрытии `retained` содержит сумму выхода 0, а `payout = 0`.
Условие `when !terminal` сохраняет доступность восстановления, когда арифметика
продолжения вызвала бы переполнение или исчерпание бюджета.

Все поля политики обязательны. Их смысл, адреса получателей и разрешённые ветки
описаны в [API](api.md) и [целочисленном ядре](core.md).

## Проверка постусловий

`ensures` задаёт свойство для локального верификатора над готовой программой.
`old(name)` — значение постоянного счётчика на входе в вызов. Сеть исполняет
скомпилированные инструкции и проверки `require`.

```sh
target/release/pruv smt noid_pruv/examples/budget.pruv --params budget.params.json --out budget.smt2
z3 budget.smt2
```

Ожидаемые ответы — `sat`, затем `unsat`. Первый устанавливает существование
успешного целочисленного исполнения. Второй устанавливает все постусловия для
каждого успешного исполнения скомпилированной программы при семантике QF_BV
Z3 и закодированной семантике инструкций ABI 3.

Входное состояние и числовой контекст — произвольные `u64`; временные регистры
начинаются с нуля. Индексы слотов ограничены `u32`, флаги логические, дедлайн
вычисляется из высоты. Модель учитывает предикаты, отказ проверок и переполнения.
Арифметика внутри постусловия тоже должна помещаться в `u64`.

Это свойство одного вызова. Инвариант всех достижимых состояний дополнительно
требует проверки начального состояния и индуктивного сохранения. Проверка
приложения включает политику, разрешённые ветки и получателей. Соответствие
исходника инструкциям проверяется сравнением с существующим native interpreter.

Для примера бюджета начальное `remaining = budget` и сохранение
`remaining <= old(remaining)` дают `remaining <= budget` после любого числа
успешных вызовов продолжения, если каждый переход использует ту же программу
и аутентифицированное состояние преемника. Из проверяемого вычитания
`remaining -= payout + fee` также следует: остаток плюс суммарные выплаты и
комиссии этих вызовов равен начальному бюджету. Восстановление закрывает
экземпляр; конечный выход определяется отдельно зафиксированной политикой.
Полное рассуждение о жизненном цикле охватывает инициализацию, все разрешённые
переходы и закрытие.

Контрпример, невыполнимая программа, неполный ответ, ошибка или таймаут приводят
к отказу проверки. Лимит Z3 — 10 секунд на запрос и 30 секунд на процесс.


Типизированные запросы для токенов, торговли и NFT описаны в [нативных финансовых шаблонах](native-templates.md).
